## 3. 需要三方拍板的 4 个决策

### 3.1 UDP 图片的目标格式与尺寸 ★ 影响最大

V0.3 的 framebuffer 是 1920×1080 XRGB8888 = **8,294,400 B/帧**，
是 A 现有 1280×720 RGB565（1,843,200 B/帧）的 **4.5 倍**。

按千兆以太网实测~114 MB/s 有效载荷估算：

| 格式 | 每帧字节 | 传输耗时 | 上限帧率 |
|---|---:|---:|---:|
| 1280×720 RGB565（A 现状） | 1,843,200 | ~16 ms | **~60 fps** |
| 1920×1080 XRGB8888（V0.3） | 8,294,400 | ~73 ms | **~13.7 fps** |

A 现有 Demo 的「60 张/秒」和 B 的 framebuffer 格式**不可兼得**。
且 FPGA 端没有缩放器（`使用说明.md:364`），缩放只能在 PC 端做。

**A 的建议**：UDP 通路**不追求满屏 1080p 帧率**，改为按用途分两条：

- **素材加载**（主要用途）：PC 端转好 XRGB8888，UDP 写入素材区 `0x0200_0000`，
  由 BitBlt 搬/合成到 framebuffer。素材不必是整屏，帧率要求低。
- **整屏投屏**（次要用途）：接受 ~13 fps，用于演示。

**请 B/C 确认**：素材区是否就是 UDP 的落点？还是希望 UDP 直接写 framebuffer 后台？

### 3.2 帧状态寄存器挂哪条总线

A 原方案挂 **APB slave 0 @ `0xF810_0000`**。已核实：

- 该地址在 `soc.h:66` 定义为 `IO_APB_SLAVE_0_INPUT`，64 KB
- 厂家实现 `apb3_top`（`jzy/co_debug_2026/par/ddr_demo_ti60_2026/src/Interrupt.v:6`）
  **是个空壳**：只实现 offset 0 的一个可写位，`apb_prdata` 恒为 0
- B 的顶层已经把它例化并接好（`ddr3_example_top.v:845`），B 也记录了
  「厂家 apb3Demo 与当前 SoC 不匹配，位流没有实现」

→ **`0xF810_0000` 实际是空闲的，A 可以整段接管，用自定义 APB3 slave 替换 `apb3_top`。**

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A：APB slave 0**（A 建议） | 64 KB 独立空间，与 BitBlt 的 AXI 控制面物理隔离；改动仅替换一个空壳模块 | 需处理 APB 与 A 的 UDP 时钟域之间的 CDC |
| B：`SYSTEM_AXI_A` 划一段（如 `0xE120_0000`） | 与 BitBlt/显示同一套 `user_clk`，无需新增总线 | 需扩 `axi_ctrl_demux`；与 BitBlt 控制面挤在同一窗口 |

**请 B 确认**：接受 A 接管 APB slave 0，还是希望统一到 `SYSTEM_AXI_A`？

### 3.3 A 的 UDP 逻辑并入哪个时钟域

A 现有顶层 `sys_clk` ≈108 MHz（9.26 ns），V0.3 平台是 **100 MHz `user_clk`**。
A 的 UDP 接收链路另有时钟域：`gmii_rx_clk`（RGMII 恢复时钟）、`rxc`。

**A 的建议**：UDP 收包逻辑保留自己的时钟域，`sys_clk` 直接改用平台的 100 MHz
`user_clk`，DDR 写通路整体搬到 `user_clk` 域与 B 的写仲裁器对齐。

**请 B 确认**：`user_clk` 是否可以给 A 的 DDR 写状态机使用？现有 DDR3 控制器
（`ddr3_parameter.vh` 的 `ASYN_AXI_CLK`、`TX_CLK_SEL`）是否需要一并调整？

> ### ⚠️ A 侧 2026-09-19 上板实测：DDR3 配置**不可逐参数混搭**
>
> A 曾按「统一两份 DDR3 配置」的思路，把 `udp_image_demo` 的 `ADDR_WIDTH`（30→28）
> 和 `ASYN_AXI_CLK`（1→0）改成 B 工程的值，但**保留了 udp 工程自己的 PHY 时钟相位**
> （`TX_CLK_SEL=0` / `TX_CLK_90EDGE_SEL=3`，B 工程是 3/0）。
>
> 实测结果：**画面花屏**。把这两个参数退回原值、只保留 RTL 修复后重编，**画面恢复干净**。
> 两组 bitstream 之间只有这两个参数不同。
>
> 两份完整配置各自都板测正常，但**混搭会坏**。
>
> **对合并的结论**：merged 顶层将基于 B 的工程，**DDR3 控制器请整份沿用 B 的配置
> （即 `ddr_demo_ti60` 的那一套）**，不要因为 A 的 UDP 通路接进来就调整其中任何一项。
> A 侧不对此提出任何参数变更要求。
>
> 若将来确实需要改，必须**整份替换 + 上板重跑校准**，不能逐参数拍板。
> 详细复盘见 A 侧 `rwj/udp_image_demo/A0-2_DDR3配置统一.md` 顶部。

### 3.4 DDR 写通路的接入方式

B 现有写仲裁是 **2-to-1**（CPU / BitBlt）。A 的 UDP 写状态机是第三个写主设备。

| 选项 | 说明 |
|---|---|
| **A：扩为 3-to-1 写仲裁**（A 建议） | 与读侧（CPU/BitBlt/显示 3 路）对称 |
| B：UDP 复用 BitBlt 的写口 | 需 B 改 BitBlt 控制逻辑，耦合更紧 |

另需确认 **AXI ID 分配**：A 现有写状态机硬编码 `awid=1`、`arid=2`；
B 的仲裁器已占用若干 ID，合并后必须重新分配，否则响应会串。

| # | 决议 | 状态 |
|---|---|---|
| ① | **`0xF8100100–0xF81001FF` 归 A**，低 256 字节（`0x000–0x0FF`）定义为**保留区** | ✅ B 已同意 |
| ② | **MVP 采用轮询**；IRQ 作为后续扩展，**优先 PLIC 源 16，不占源 30** | ✅ 已定 |
| ③ | **可立即冻结**，但需补三点：最终 BRESP 后发布、跨时钟握手、只保留最新快照 | ✅ A 接受并修订设计 |

### ③ 的三点补充如何落到设计里

**(a) 最终 BRESP 后发布 —— 这条推翻了我原来的时序。**

原设计是 `st_*` 在 `frame_done` 那一刻锁存。但 `frame_done` 由 END 控制包产生，
**此时 AXI 写流水线里可能还有未返回的 BRESP**。快照会在最后一次写响应到达前发布，
把本该 `FRAME_OK=0` 的帧报成好的 —— 恰好是这接口存在要防的那类错误。

**改为**：`frame_done` 置起后，等**写流水线排空**（可用写状态机回到 `W_IDLE`、
或加一个未完成写计数归零作为条件）再发布快照。发布前 `SEQ` 不递增，
所以软件看不到中间状态。

**(b) 跨时钟握手。**

发布逻辑涉及两个时钟域：

```
gmii_rx_clk (125MHz)   →  user_clk (100MHz)
帧数据通路、BRESP 检测       APB/AXI 寄存器接口、C 组读
```

快照需要跨域传：`{frame_id, slot, base, rx_bytes, expect_bytes, status}` ≈ 140 bit。
用 **toggle 握手 + 双缓冲**（发布方翻转 toggle，接收方同步后整体锁存），
或直接用已有的 AXI 写响应通道作为同步点。**不能用多 bit 打两拍**——
各 bit 到达时间不同会产生撕裂快照。

**(c) 只保留最新快照。**

不排队、不累积。`st_*` 寄存器组被每一帧覆盖；软件靠 `SEQ` + seqlock 读法
判断有没有新帧、读到的整组是否属于同一帧（见 §4）。

## 4. A 侧接口的新形态（收窄后）

V0.3 已经覆盖了「显示是否换帧」这件事（`FRAME_COUNT`/`SWAP_DONE`），
所以 A 的帧状态接口只保留 **B 和 C 都不覆盖** 的部分：

**UDP 收帧本身的完整性 —— 这一帧收全了吗、写到哪了。**

**基地址 `0xF8100000`（APB slave 0），本模块占 `0x100–0x1FF`。**
低 256 字节（`0x000–0x0FF`）为保留区。模块内用 `paddr[7:0]` 译码。

| 偏移 | 名称 | R/W | 说明 |
|---|---|---|---|
| `0x100` | `FRAME_ID` | R | 快照：帧号 |
| `0x104` | `SLOT` | R | 快照：写入槽位 |
| `0x108` | `BASE_ADDR` | R | 快照：DDR 基址 |
| `0x10C` | `RX_BYTES` | R | 快照：实际写入字节数 |
| `0x110` | `EXPECT_BYTES` | R | 快照：START 声明字节数 |
| `0x114` | `STATUS` | R | 快照位图，见下 |
| `0x118` | `ACK` | **W** | 写 SEQ 值；匹配才清 `ERR_STICKY`。**只写，读回 0** |
| `0x11C` | `SEQ` | R | 完成帧计数器，单调递增 |
| `0x120` | `SWAP_SEQ` | R | 显示端实际切屏次数 |
| `0x124` | `SWAP_FRAME` | R | 切上屏的是哪一帧 |
| `0x128` | `ERR_STICKY` | R/W | 跨帧累积错误，写任意值清 |
| `0x12C` | `ID` | R | 魔数 `0x46524D31`（"FRM1"） |
| `0x130` | **`LIVE_STATUS`** | R | **实时状态，不参与快照** |

**`STATUS`（`0x114`）—— 纯快照，不含任何实时位**：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `DONE` | 恒为 1（快照必然描述一个已完成的帧） |
| 1 | `FRAME_OK` | **整帧成功**，含 `!SEQ_ERR && !FIFO_OVF && !BRESP_ERR && !BYTES_MISMATCH` |
| 2 | `SEQ_ERR` | 断号/重复，或 END 的 frame_id 与 START 不一致 |
| 3 | `FIFO_OVF` | 接收/控制 FIFO 溢出丢拍 |
| 4 | `BRESP_ERR` | AXI 写响应错误（SLVERR / DECERR） |
| 5 | `BYTES_MISMATCH` | `RX_BYTES != EXPECT_BYTES` |
| 6 | `SWAPPED` | 本帧**请求**了切屏（实际是否切了看 `SWAP_SEQ`） |
| 7–15 | — | 保留 |

> **`CAL_DONE` 已从 `STATUS` 移出**（2026-09-19 B/C 决议）。原设计把它作为 bit8
> 实时读，破坏了「`STATUS` 是纯快照」这条语义。现在归 `LIVE_STATUS`。
> 这样 `STATUS` 的任何一个读都完整描述同一帧，软件不需要判断哪些位是实时的。

**`LIVE_STATUS`（`0x130`）**：bit0 `CAL_DONE`；其余保留。

**`ERR_STICKY`（`0x128`）**：bit0 `SEQ_ERR`｜bit1 `FIFO_OVF`｜bit2 `BRESP_ERR`｜
bit3 `ARP_MISS`｜bit4 `BYTES_MISMATCH`。跨帧累积，写任意值清。

> `ARP_MISS` 只在 `ERR_STICKY` 里，不在 `STATUS` 快照里 —— 它描述 ACK 发送通路，
> 与帧数据无关，且发生时刻与帧完成不同拍。

**`ACK`（`0x118`）只清 `ERR_STICKY`，不修改快照。** 写 SEQ 值；不匹配则忽略
（说明软件读到的快照已被新帧覆盖，此时清会把新帧的错误一并抹掉）。

**这组寄存器解决的是 A 侧独有的问题**：UDP 收帧的完整性判据
（`top.v:644` 的 `frame_ok = frame_bytes_ok && !frame_seq_err && !fifo_ovf && !bresp_err`）
目前只能通过 UDP 回执送回 PC（`top.v:721`），上了 CPU 之后 C 组可以直接读。

**A 侧已完成的 RTL 改动**（可复用，见 `rwj/udp_image_demo` 提交 `c99dd51`）：

- `BRESP` 错误检测 + 粘滞位，`frame_ok` 纳入 `!bresp_err` — 原来 `bresp` 全文件只出现 2 次，
  **没有任何逻辑读它**，DDR 写失败时 `frame_ok` 照样是 1
- ACK 回执位宽 bug 修复 — `udp_img_rx.v` 把 192 位透传口声明成 `[127:0]`，
  **magic 和 frame_id 被静默截断，`--ack`/`--retry` 从实现至今一直失效**

> 第 2 条对历史结论有影响：**2026-09-18 之前所有「回执正常」的判断都不可信。**
> 图像显示本身不受影响（收图和显示走另一条路径）。

寄存器位定义与 `frame_poll()` 驱动，待 §3.2 总线归属确定后由 A 出 V0.2 定稿。

## 附二：UDP 回执（`--ack` / `--retry`）的已知缺陷（2026-09-19 上板实测）

**结论：这两个开关目前仍然不可用，且原因不止一个。图像传输本身不受影响。**

A 侧在 2026-09-18 修掉了回执 payload 的位宽截断（`udp_img_rx.v` 的透传口 `[127:0]`→`[191:0]`），
并在 2026-09-19 重编上板实测。**实测结果：板子在整帧完成后不发送任何回执报文。**

板端排查证据（`tcpdump -i enp3s0 -Q in 'arp or udp port 8080'`，发送含 `FLAG_ACK` 的完整帧）：

```
全程只收到 1 个入向包：
  20:34:58.592011 ARP, Reply 192.168.0.2 is-at 00:0a:35:0a:fe:c0
→ 没有任何 ARP 请求（板子没问过 who-has 192.168.0.3）
→ 没有任何 UDP 回执
```

已排除的方向：
- `ufw` 防火墙（实测 `ENABLED=no`，规则未加载）
- PC/RTL 的 flag 位定义（`0x01/0x02/0x04/0x08/0x10/0x20` ↔ bit 0–5 完全一致）
- `destination_ip_addr` 未连接（实际接的是 `DST_IP` = 192.168.0.3）
- `ack_payload` 端口位宽（修复已确认生效，`udp_img_rx.v:58` 已是 `[191:0]`）
- 控制字 FIFO 布局（`ctrl_fifo.WrData({byte_offset, payload_len, slot, flags})`，
  `F_ACK=3` 确实落在 flags 的 bit 3）

**读代码发现的两个确定性缺陷**（`udp_ack_tx.v`）：

1. **24 字节回执只写进去 23 字节。** `ram_wr_data_r` / `ram_wr_en_r` 是寄存器，
   写进 MAC 的 TX RAM 的字节比 `byte_cnt` 慢一拍；状态机在 `byte_cnt == ACK_LEN-1`
   时就切到 `A_SEND`，**第 24 字节（XOR 校验和低字节）从未写入**。

2. **主动 ARP 的单拍脉冲会被丢掉。** `arp_request_req` 只拉高一个时钟周期，
   而 `arp_tx` 只在 `IDLE` 状态采样它。PC 每次解析邻居（ping / 邻居表变 STALE）
   都会让 `arp_tx` 忙一轮，此时脉冲丢失 → ARP 缓存仍为空 →
   回执会以广播 MAC (`ff:ff:ff:ff:ff:ff`) 发出。

> **该模块作者自己的注释**：`udp_ack_tx.v:23` —— 「这条路径没有在真实硬件上验证过，
> 所以默认不启用。」上板现象与「状态机根本没被触发」一致，说明除上述两条外
> 可能还有其他缺陷。

**处置决定（2026-09-19）**：**暂不修复。** 理由：
- 该功能是调试辅助（PC 端提示原文：「图片本身很可能已经正常显示了，回执只是额外确认」），
  不是赛题要求，且不影响图像传输
- 该模块在 UDP 通路迁移到 B 的工程时**本来就要重写**（写入目标从 4 槽 × 2 MiB
  改为 V0.3 的 Framebuffer / 素材区布局），现在深入修复可能是白做
- 修复的唯一可靠手段是补一个带 MAC 握手模型的 testbench（纯读代码已证明会漏），
  这属于 M1「最小 RTL Testbench」交付物的一部分，应在迁移后随新模块一起做

**待办**：迁移时按新接口重写回执通路，并补 testbench；不要沿用 `udp_ack_tx.v`。
