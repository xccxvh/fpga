# UDP 传图到 FPGA：运行说明

> **独立 Demo 专用。** 本文中的 slot、按键、自动轮播和直接换屏不属于联合工程协议。
> 三方联合接入必须遵守
> [`../../07_docs/interfaces/unified_fpga_interface_spec_v1.0.md`](../../07_docs/interfaces/unified_fpga_interface_spec_v1.0.md)，
> 不得把本文当作接口规范。

本工程的数据链路是：

```text
PC 图片 -> 1280×720 RGB565 -> UDP -> RGMII -> DDR3 -> HDMI
```

## 1. 准备工作

需要 Ti60F225 开发板、JTAG 下载器、HDMI 线、显示器，以及连接 PC 和
开发板的网线。PC 端需要 Linux、Python 3、Pillow 和 NumPy：

```bash
cd "/media/rwj/ZX1 2TB/FPGA2026/udp_image_demo"
python3 -m pip install --user pillow numpy
python3 -m py_compile pc/*.py
```

最后一条没有输出，表示 PC 端脚本通过语法检查。

> 当前代码只实现了有线以太网传图，没有 Wi-Fi、USB、UART 或 SD 卡传图。
> 没有网线时不能传入新图片。已写入 DDR3 的图片在不断电时可继续显示，
> 断电后不保留。

## 2. 编译和烧录 FPGA

工程已有编译好的文件：

```text
fpga/outflow/ddr3_hdmi_test.bit
```

RTL 未修改时，可直接用 Efinity Programmer 通过 JTAG 烧录。如需重新编译：

```bash
cd "/media/rwj/ZX1 2TB/FPGA2026/udp_image_demo/fpga"
./build.sh
```

`build.sh` 当前把 Efinity 路径写为：

```text
/home/rwj/Efinity/efinity/2026.1/bin/efx_run
```

如果安装路径不同，先修改 `fpga/build.sh` 中的 `EFX_BIN`。编译后应生成
`fpga/outflow/ddr3_hdmi_test.bit`。

烧录后连接 HDMI 并给板子上电：

- `b_led[0]`：DDR3 校准完成。
- `b_led[1]`：HDMI 显示 FIFO 已启动。

刚上电时 DDR3 还没有图片，显示黑屏或未知内容并不异常。

## 3. 连线和配置 PC 网卡

用网线直连 PC 和开发板。固定参数为：

```text
FPGA IP    192.168.0.2
PC IP      192.168.0.3/24
UDP 端口   8080
链路模式   1000M 全双工
```

查看网卡名：

```bash
ip -br link
```

以 `enp3s0` 为例，实际使用时换成自己的有线网卡名：

```bash
sudo ip link set enp3s0 up
sudo ip addr replace 192.168.0.3/24 dev enp3s0
ip -br addr show enp3s0
ip route get 192.168.0.2
sudo ethtool enp3s0 | grep -E 'Speed|Duplex|Link detected'
```

`ip route get` 应显示经过该有线网卡，源地址是 `192.168.0.3`。`ethtool` 应显示
`1000Mb/s`、`Full` 和 `Link detected: yes`。当前 RTL 把 MAC 固定为 1000M，
如果只协商到 100M，不能保证正常收图。

## 4. 发送第一张图片

先检查转换和分包，不实际发送：

```bash
cd "/media/rwj/ZX1 2TB/FPGA2026/udp_image_demo/pc"
python3 send_image.py "/路径/图片.jpg" --dry-run
```

正常输出应包含：

```text
屏幕       : 1280 x 720
数据大小   : 1843200 Byte
总包数     : 1440 个 DATA 包 + START/END
```

然后实际发送：

```bash
python3 send_image.py "/路径/图片.jpg" --gap 0.001
```

第一次建议使用 `--gap 0.001`，给板端 UDP RAM 和 DDR3 留出时间。成功后
可改回默认的 `0.0002` 测试更快速度。

图片适配方式：

```bash
# 保持比例完整显示，默认补黑边
python3 send_image.py picture.jpg --mode fit --gap 0.001

# 保持比例铺满，边缘可能被裁掉
python3 send_image.py picture.jpg --mode fill --gap 0.001

# 强制拉伸，可能变形
python3 send_image.py picture.jpg --mode stretch --gap 0.001
```

## 5. 预载多张图片和按键切换

按键只在槽位 0～3 之间循环，按键演示只使用这四个槽位：

```bash
python3 send_image.py 1.jpg --slot 0 --no-swap --gap 0.001
python3 send_image.py 2.jpg --slot 1 --no-swap --gap 0.001
python3 send_image.py 3.jpg --slot 2 --no-swap --gap 0.001
python3 send_image.py 4.jpg --slot 3 --no-swap --gap 0.001
```

`--no-swap` 只写入槽位，不立即切屏。发完后：

- KEY1 / `GPIOL_07`：上一张。
- KEY3 / `GPIOL_03`：下一张。

如果要连续更新，可以用 0/1 槽位交替的双缓冲：

```bash
python3 send_image.py picture.jpg --dbuf --gap 0.001
```

`--dbuf` 的槽位由**板端**决定：FPGA 会挑"当前没在显示"的那一块写，写完自动
切过去。PC 不需要知道板子现在显示哪个槽位，所以重启 PC、清缓存、按过按键
都不会让它写错到正在显示的那块上。

## 5.5 自动轮播（不用按键，自动切图）

预载好几张之后，可以让板子自己循环切，不用手动按键。

```bash
# 先预载 4 张（--no-swap 只存不显示）
python3 send_image.py a.jpg --mode fill --slot 0 --no-swap
python3 send_image.py b.jpg --mode fill --slot 1 --no-swap
python3 send_image.py c.jpg --mode fill --slot 2 --no-swap
python3 send_image.py d.jpg --mode fill --slot 3 --no-swap

# 开启轮播：每 1 帧切一张 —— 这是本架构的上限，60 张/秒
python3 send_image.py --config-only --auto-cycle 1

# 慢一点：每 30 帧切一张，也就是 2 张/秒
python3 send_image.py --config-only --auto-cycle 30

# 关掉
python3 send_image.py --config-only --auto-cycle 0
```

`--config-only` 表示只下发设置、不发图片，**当前画面不动**。

### 关于速度

| `--auto-cycle N` | 效果 |
|---|---|
| `1` | 每帧切一张，**60 张/秒**（最快） |
| `2` | 30 张/秒 |
| `30` | 2 张/秒 |
| `0` | 关闭 |

**60 张/秒已经是上限**——切屏只是改一个读基地址，而且落在消隐期，所以再快也不可能，也不会撕裂。N=1 时每张图只显示 16.7ms，肉眼看是连续流动的模糊；想看清每张图建议设 30~60。

### 和按键的关系

轮播开着的时候**按键仍然有效**，优先级是：

```
按键  >  发图时整帧完成的自动切屏  >  自动轮播
```

所以轮播开着时，PC 发一张新图仍然能立刻切过去，不会被轮播抢掉。

轮播在槽位 0..3 之间循环（`SLOT_COUNT`）。发普通图片不会改变轮播设置——只有带 `--auto-cycle` 才会动。

## 6. ACK 回执与整帧校验

```bash
python3 send_image.py picture.jpg --gap 0.001 --ack
```

ACK 要求 PC 地址是 `192.168.0.3`。这项功能尚未在真实硬件上验证，因此
"没等到 ACK"不一定表示图片没有收到，应先看 HDMI 画面。

### 板端怎么判定"整帧完整"

四项全过才算完整，**任何一项不过都不会切屏**：

| 检查 | 抓什么 |
|---|---|
| 字节数 == START 声明值 | 整包丢失 |
| `packet_idx` 严格 0,1,2,… 连续 | 丢包、重复包、乱序 |
| DATA/END 的 `frame_id` == START 的 | 两个发送程序串帧写同一槽位 |
| 三个跨时钟 FIFO 没有溢出丢拍 | 发得太快，板端来不及搬 |

> 只比字节数是不够的：「丢一个包、又重复另一个包」字节数照样相等。
> 所以必须查 `packet_idx` 连续性 —— 对应回执报告里"包序号"那一行。

### 帧校验和

板端对每个真正写进 DDR 的 128-bit 字累加 `sum`（64 位回绕）并异或 `xor`，
整帧结束报给 PC，两边逐位比对。它**不是**用来抗信道误码的（以太网 FCS 已经
保证逐包完整性，坏帧在 MAC 层就被丢了），而是用来查 FPGA 这边的写入路径：
槽位基地址算错、AXI 写偏、FIFO 溢出后错位 —— 这类错误字节数和包序号都对得上，
只有校验和能看出来。

### 失败自动重传

```bash
python3 send_image.py picture.jpg --ack --retry 3 --gap 0.001
```

板端报不完整时整帧重发，最多 3 次，每次用新的 `frame_id`。默认 `--retry 2`。

### 回执报告怎么看

```
字节数     : OK / 不完整，少了 N Byte
包序号     : OK（0..N-1 连续，无重复）/ 断号/重复
板端 FIFO  : OK / 溢出过
帧校验和   : OK / 不一致

结论       : 帧完整，板端会在下一个 VSYNC 切过去。
             或者：这一帧不可用，板端**没有**切屏。
```

## 7. 故障排查

### 发送完成但屏幕没变

1. 确认 `b_led[0]` 表示 DDR3 已校准。
2. 确认烧录的是本工程的 bitstream。
3. 确认 PC 地址和路由正确，并已协商到 1000M。
4. 把发送间隔增大后重发：

```bash
python3 send_image.py picture.jpg --gap 0.002
```

5. 抓包检查（替换网卡名）：

```bash
sudo tcpdump -ni enp3s0 'arp or icmp or udp port 8080'
```

### 花屏、缺块或不切屏

**先分清"花屏"和"不切屏"**：

- **花屏/缺块**：这一版基本不该出现了。整帧不完整时板端不会切屏，
  所以屏幕上要么是完整的旧图，要么是完整的新图。
  如果还看到花屏，说明是 DDR3 读侧或 HDMI 的问题，不是传输的问题。

- **不切屏（画面一直是上一张）**：这是**故意的保护行为** —— 这一帧没收全。
  加 `--ack` 看具体原因：

```bash
python3 send_image.py picture.jpg --gap 0.001 --ack --retry 3
```

  - 报"包序号断号" → 真丢包，加大 `--gap`
  - 报"板端 FIFO 溢出" → 发得太快，加大 `--gap`
  - 报"帧校验和不一致" → 不是丢包，是板端写 DDR 的路径有问题，报出来给我看
  - 没等到回执 → 回执本身是实验功能，先看 HDMI 画面

- 保持默认 `--chunk 1280`，chunk 必须是 16 字节的倍数。
- 不要同时运行多个发图进程，否则帧会互相交错。
- 使用 `--no-swap` 时，屏幕本来就不会立即改变。

### 端口 8080 已被占用

```bash
ss -lunp | grep ':8080'
```

不使用 `--ack` 时，可临时改 PC 本地端口：

```bash
python3 send_image.py picture.jpg --local-port 18080 --gap 0.001
```

### 颜色不对

`send_image.py` 会生成与 FPGA 匹配的小端 RGB565。自己生成 `.bin` 时，文件必须是
1280×720、RGB565、小端、共 1843200 字节。

## 9. 显示为什么不会错位（技术说明，改 RTL 前必读）

读状态机是**自由跑**的：它把整个 framebuffer 读成一个连续的 128-bit 字流，
显示端按固定的 115200 字/帧消费。两者之间只有读 FIFO 缓冲，**没有任何天然的
对齐机制**。

后果：读状态机回绕的那一刻，FIFO 里还剩 K 个字没被显示端取走，画面就会整体
旋转 K 个字。因为一个字 = 8 像素、一行 = 160 字：

```
水平偏移 = (8K mod 1280) 像素
垂直偏移 = floor(K / 160) 行
```

表现是"画面往右下移，移出去的部分从左边和上边绕回来"。**这个 bug 原工程就有**，
2026-09-18 才定位并修掉。

**修法**：读状态机回绕后先停在 `R_DRAIN`，等显示端走到**消隐期开头**
（`hcnt==0 && vcnt==V_ACTIVE`）再继续读。那一刻 FIFO 正好被取空、错位归零，
而且后面还有 30 行消隐给读状态机从 DDR 预取。

> ⚠️ 参考点**不能**选 `vcnt==0`（有效画面第一行）。那是显示端立刻就要数据的
> 时刻，而 AXI 从 DDR 读数约 250ns ≈ 19 个像素，第 0 行开头会饿死变黑 ——
> 这一行少消费的像素会让整帧字相位错开，结果就是"上下对了、左右还偏"。
> 这个中间版本实测过，确实是这个现象。

**改动读状态机时务必保留 `R_DRAIN`。** 想验证有没有改坏，发
`images/_test/border4.png`（上红/下蓝/左黄/右绿，四边有指向三角形）——
四条边全部贴边正确才算没坏。

## 10. 已知限制

- 只支持有线以太网传入新图片。
- HDMI 固定为 1280×720，缩放在 PC 端完成，FPGA 端没有缩放器。
- PHY/MAC 按 1000M 模式使用，未实现 10M/100M 适配（沿用 demo4，靠 PHY 默认
  自协商，没有完整 MDIO 配置）。链路当前实际跑在 1000M 上。
- **ACK 回执没有在真实硬件上验证过**，默认关闭。不加 `--ack` 时板端回执
  状态机停在 IDLE，对收图链路零影响。
- 时序已收敛（`outflow/ddr3_hdmi_test.timing.rpt` 里 0 条负 slack）。
  之前那 20 条负裕量是 DC_FIFO 内部异步复位握手被误分析，已经在约束里排除。
